# BR: Slug & Display-ID Based Routing

**Status:** Locked (with open items flagged below)
**Applies to:** Workspace, Project, Todo entities
**Related verticals:** Workspace (done), Project (in progress), Board/BoardColumn (not started), Todo (blocked on Board/BoardColumn)

---

## 1. Purpose

Define how Workspace, Project, and Todo entities are addressed in URLs, and how the frontend and backend resolve those URLs to data. Goal: clean, Linear-style flat URLs that remain stable even as todos move between boards/columns.

---

## 2. Entities & Identifier Type

| Entity     | Identifier used in URL | Generated by | Mutable? |
|------------|------------------------|--------------|----------|
| Workspace  | `slug`                 | Backend      | No       |
| Project    | `slug`                 | Backend      | No       |
| Todo       | `display_id` (e.g. `wr-546`) | Backend | No       |

- Slugs are generated **only** at creation time (workspace/project creation) and never regenerated, even if the display name changes later.
- Workspace slugs are globally unique. Project slugs are unique within their workspace.
- `display_id` = `prefixCode` (immutable, unique per workspace, set at project creation) + `display_id_seq` (incrementing per-project sequence, stored not computed, never reused).
- `prefixCode` is stored and displayed as entered (e.g. `WR` on the Kanban card badge), but the **URL-facing `display_id` is lowercase-only** (see §6.2 Case Sensitivity). The backend generates the lowercase route form; the frontend never derives it by lowercasing on the client.

**Frontend rule:** never generate or guess a slug/display_id client-side. Always read the value from the API response object and use it as-is for routing and linking.

## 3. URL Structure (Locked — Flat/Linear-style)

```
/{workspaceSlug}                                  → workspace home/dashboard
/{workspaceSlug}/{projectSlug}                    → project default board view
/{workspaceSlug}/{projectSlug}/{displayId}        → todo detail (board-agnostic)
/_/settings                                       → platform/account-level settings
/_/notifications                                  → platform-level notifications
/_/profile                                        → user profile
/{workspaceSlug}/_/settings                       → workspace-level settings
/{workspaceSlug}/_/members                        → workspace-level members
```

Examples:
```
/acme
/acme/website-revamp
/acme/website-revamp/wr-546
/_/settings
/acme/_/settings
```

Delimiter convention (see §3.1) replaces the reserved-words approach — `_` can never appear in a generated slug, so platform- and workspace-level routes are structurally safe from collision with any slug, without needing a blocklist.

### 3.1 Underscore Delimiter Convention (Locked — replaces reserved-words list)

Platform-level and workspace-level pages (settings, notifications, members, profile, etc.) are namespaced under a literal `_` path segment, rather than relying on a blocklist of reserved words:

```
/_/{page}                        → platform-level page (not scoped to any workspace)
/{workspaceSlug}/_/{page}        → workspace-level page (scoped to that workspace)
```

**Why this replaces a reserved-words list entirely:** standard slugify (lowercase, hyphens for spaces) never produces an underscore in its output. This means `_` as a path segment can **never collide with a real workspace or project slug**, by construction — no blocklist to maintain, no risk of forgetting to add a new reserved word before shipping a new platform page.

- Slug generation (backend) doesn't need to explicitly reject `_` — it's already impossible for standard slugify to emit one. A test asserting this stays true is enough; no runtime validation needed.
- Frontend router matches `_` as a literal segment with top precedence, before the generic `{workspaceSlug}` / `{projectSlug}` catch-alls.
- This applies at **both** levels: `/_/...` for platform-wide pages (account settings, notifications — not scoped to any single workspace) and `/{workspaceSlug}/_/...` for workspace-scoped pages (workspace settings, members).

No `/workspaces/` or `/projects/` path prefixes. No board/column segment in the URL at any level — board/column context is resolved client-side after fetching the todo, not encoded in the route.

## 4. Backend Resolution Logic

- Todo lookup resolves by the tuple **`(projectSlug, displayId)`**, deliberately **board-agnostic**.
- This guarantees a todo's URL remains valid even after it moves between boards or columns (Kanban ↔ Sprint, column to column) — the route never encodes board/column state.
- Suggested endpoint shape:
  ```
  GET /projects/{projectSlug}/todos/{displayId}
  ```
  Internally resolves the todo regardless of its current board/column.

---

## 5. Frontend Rules (for Antigravity to enforce)

1. Never construct a slug or `display_id` client-side — always consume it from the API response.
2. Store slugs/display_ids in Redux state exactly as returned; use them as route params directly.
3. Any link to a todo (board card, search result, notification) must use the `display_id` from that todo object — never reconstruct it from `prefixCode` + sequence number on the frontend.
4. On project/workspace switch, re-fetch by slug from the URL param rather than trusting cached state to match.
5. Route guard: the third path segment (`{displayId}`) should be matched against a display-ID pattern (see §7 Open Items) so the router doesn't misinterpret it as a generic slug.

## 6. Locked Decisions (Case Sensitivity & Route Namespacing)

### 6.1 Underscore Delimiter (Platform/Workspace Route Namespacing)
See §3.1 — locked convention. Replaces the reserved-words approach entirely. No list to maintain; collision is structurally impossible since slugify never emits `_`.

### 6.2 Case Sensitivity — Lowercase Only (Locked)
- All slugs (workspace, project) and `display_id` route values are **lowercase only**.
- Backend generates slugs and `display_id` route values in lowercase at creation time — no mixed case ever produced.
- Backend does **not** auto-normalize uppercase input on resolution — a request for `/acme/website-revamp/WR-546` is **not** rewritten or accepted; it resolves as not-found. Only the exact lowercase form is valid.
- Frontend must always link using the lowercase `display_id`/`slug` values returned by the API — never uppercase for display in a way that gets round-tripped into a link (badge display like `WR-546` on a card is fine visually, but the `href` underneath must use the lowercase `display_id`).

## 7. Open Items to Confirm

1. **Display-ID pattern guard** — Frontend router needs an explicit regex (e.g. `^[a-z]+-\d+$`) to distinguish a `displayId` segment from an invalid/unknown project slug, so malformed URLs fail predictably (404) rather than being misrouted. Also needed on the backend resolution endpoint as an early-exit validation before hitting the DB.

- **Backend:** `prefixCode` and `display_id_seq` fields + generation logic exist as part of the Project creation transaction. **Not yet wired** into Todo creation/resolution endpoints — blocked on Board/BoardColumn verticals.
- **Frontend:** Not yet consuming `display_id`-based routing. Planned after Board/BoardColumn stabilize on the backend.

## 9. Sequencing Note

This routing scheme should be implemented on the frontend only after:
1. Board/BoardColumn verticals are complete on the backend.
2. `TodoServiceImpl`'s known gap (project/column not set before save) is resolved.
3. Todo resolution endpoint (`GET /projects/{projectSlug}/todos/{displayId}`) is live and stable.

Building frontend routing against an unstable Todo API risks rework, consistent with the general "stabilize backend contracts before frontend work" sequencing already agreed for this project.
